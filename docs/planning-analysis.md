# 기획문서 종합 분석

## 1. 결론과 분석 범위

**현재 문서는 제품 방향과 초기 설계를 논의하기에는 충분하지만, 그대로 개발·출시 기준으로 승인하기에는 부족하다.** 문서 파일의 존재와 기획의 완성은 다르다. 이전 파일 수·키워드·링크 검증은 문서 간 의미적 일관성을 보장하지 않는다.

검토 범위는 보강 전 표준 기획 14개, planning README, 기존 상세 설계 6개, CONTEXT.md 총 22개·3,315줄이다. 제품/일정, UX/디자인, 기술/데이터, 보안/운영을 나누어 대조했다. 아래 경로와 행 번호는 **보강 전 분석 기준선(snapshot)** 이므로 현재 문서의 행 번호와 달라질 수 있다. 현재 정본은 `docs/planning/README.md`와 각 planning 문서이며, 분석에서 지적한 항목은 보강본에 반영했다.

- 실제 앱의 결함·취약점·접근성 위반을 재현한 결과가 아니라 **명세 검토**다.
- 이번 분석에서 웹사이트를 재조사하거나 고객 인터뷰·부하테스트·법률 검토를 수행하지 않았다.
- 가격·공급자·스택이 미정인 것 자체는 오류가 아니다. 다만 결정 없이 해당 기능을 구현하거나 출시할 수는 없다.
- 기존 기획은 수정하지 않았다. 아래 수정안과 역할 배정은 승인 전 제안이다.

## 2. 잘 정리된 부분

1. 국내 개별주식·고객용 웹이라는 경계와 주문/계좌/ETF 제외가 명확하다.
2. 신호 발생 시각·알고리즘 버전·근거·위험 고지를 핵심 가치로 다룬다.
3. 현재 상태와 append-only 이력을 구분하고 API·스트림 서버 권한 검증을 요구한다.
4. 지연·stale·부분 장애를 정상 화면의 일부로 설계하려는 방향이 적절하다.
5. 디자인 승인, 대표 종목 수직 슬라이스, 공급자·법무 출시 게이트가 있다.
6. 접근성·반응형·보안·개인정보를 뒤늦은 부가 작업이 아닌 요구사항에 포함했다.

이 원칙은 유지하되 구현 가능한 계약과 검증 기준으로 내려야 한다.

## 3-1. 이번 보강에 반영한 조치

분석 이후 기존 문서를 직접 수정해 다음을 반영했다. 아래는 설계 문서의 보강 완료이지 구현·운영 검증 완료가 아니다.

- `docs/planning/README.md`를 정본 인덱스로 지정하고 기존 상세 문서를 참고자료로 명시했다.
- `decision-log.md`를 추가해 제안·승인·미결정 상태와 결정 책임자를 분리했다.
- MVP에서 자연어 스크리너·AI 점수·저장 필터·고도화 성과·인사이트를 후속/별도 승인 범위로 정리했다.
- 신호 상태·데이터 신선도·연결·entitlement를 분리하고, 방향을 유추하는 필터·정렬·집계·캐시까지 권한 경계에 포함했다.
- `(streamKey, epoch, sequence)`, snapshot cursor/replay, outbox 원자성, watchdog effective status, 열린 연결 revoke를 TRD/API/DB/보안/티켓에 연결했다.
- 결제 redirect와 entitlement 활성화를 분리하고 pending·해지예정·환불·역순 웹훅 전이를 명시했다.
- 구매 이후 사용자 흐름, 관심목록 재방문·삭제, 모바일/접근성/장애 프로토타입, PRD 추적표와 수직 슬라이스 티켓을 추가했다.
- 기존 상세 6개 문서에는 planning 정본 링크와 충돌 우선순위를 표시했다.

## 4. 우선 해결할 정합성·기술 문제

우선순위는 **P1: 관련 구현/출시 전 해소**, **P2: 상세 설계 승인 전 보완**이다. 위험의 실제 발생 여부나 CVSS 점수가 아니다.

### F01 · P1 · 계약의 기준 문서가 실질적으로 두 벌이다

- 근거: `docs/planning/08-api-data-contract.md:30-40`, `docs/stock-platform-api-contract.md:123-164`.
- 예: 수급은 `/flows` 대 `/supply-demand`, 결제 시작은 `/subscriptions/checkout` 대 `/billing/checkout`, 권한은 `/entitlements/me` 대 `/me/entitlements`다.
- 영향: 화면·서버·웹훅 등록·테스트가 서로 다른 계약으로 작성될 수 있다.
- 조치: 단일 기준 OpenAPI/이벤트 schema를 승인하고 기존 상세 문서와 planning 문서의 역할을 명시한다. 초안 차이를 무조건 별칭 API로 구현하지 않는다.

### F02 · P1 · DTO·오류·신호 상태가 통일되지 않았다

- 근거: `CONTEXT.md:35`, `docs/planning/06-design-plan.md:51`, `docs/planning/08-api-data-contract.md:46-76`, `docs/stock-platform-api-contract.md:84-93`.
- 용어집 상태는 ACTIVE/SUSPENDED/EXPIRED, 디자인에는 active/expiring/expired/cancelled/validating이 있다. expiring이 저장 상태인지 유효기간 기반 표시인지 불명확하다.
- ticker/symbol, direction/signalType, evidence/factors, ENTITLEMENT_REQUIRED/PREMIUM_REQUIRED도 다르다.
- 조치: 방향·유효성·신선도·연결·권한을 별도 축으로 정의하고 상태 전이표와 UI 매핑을 공유한다. 중립 신호와 데이터 없음도 구분한다.

### F03 · P1 · 순번 비교 범위가 불명확하다

- 근거: `docs/planning/08-api-data-contract.md:86-90`, `docs/planning/09-database-design.md:57`, `docs/planning/09-database-design.md:121`.
- DB는 종목별 sequence지만 클라이언트는 단순 lastSequence로 서술한다. 다종목 스트림·시세/신호 동시 구독의 커서 키가 없다.
- 영향 예: A종목 100 수신 후 B종목 2를 오래된 이벤트로 버릴 수 있다.
- 조치: 순번 발급 주체·범위·재시작 epoch·저장 방식과 `(streamKind, ticker, epoch)` 같은 비교 키를 명시한다. 구체적인 키는 전략 수와 스트림 구조 결정 후 확정한다.

### F04 · P1 · 스냅샷과 실시간 구독 사이 유실 가능성이 남는다

- 근거: `docs/stock-platform-data-model.md:366-375`, `docs/stock-platform-api-contract.md:180-189`, `docs/planning/07-trd.md:34`.
- 스냅샷 조회 뒤 구독하기 전 발생한 이벤트는 다음 이벤트가 없으면 gap조차 감지하지 못한다.
- 조치: 일관된 snapshot cursor와 resume/replay 또는 선구독 버퍼링을 정의한다. 재생 보존 한도 초과·유효하지 않은 커서·전송 중 스냅샷 변경도 시험한다.

### F05 · P1 · 저장과 이벤트 발행의 원자성이 없다

- 근거: `docs/stock-platform-data-model.md:315-325`, `docs/stock-platform-system-architecture.md:193-205`.
- 저장 뒤 발행 전에 중단되면 현재값은 바뀌었지만 이벤트는 전달되지 않을 수 있다. 중복 방지 ID만으로 해결되지 않는다.
- 조치: 현재 상태·이력·outbox의 원자 저장 또는 동등한 신뢰성 설계를 결정한다. 발행 재시도·소비 checkpoint·종목별 동시 계산 제어를 명시한다.

### F06 · P1 · 당시 근거와 replay 재구축을 보장하지 못한다

- 근거: `CONTEXT.md:32-33`, `docs/planning/09-database-design.md:60-63`, `docs/planning/09-database-design.md:124`, `docs/stock-platform-data-model.md:321`.
- 근거는 signal_id에 연결되고, 같은 상태에서는 이벤트를 만들지 않는다. 방향은 유지되지만 근거·버전·강도가 바뀌는 경우의 이력 정책이 없다.
- 조치: 사용자에게 보여주는 신호 전환과 내부 평가 revision을 구분한다. 이벤트/revision별 불변 근거와 완전한 재구축 필드를 정의한다.

### F07 · P1 · 엔진 장애 시 유효 상태를 누가 바꾸는지 불명확하다

- 근거: `docs/planning/07-trd.md:71`, `docs/stock-platform-system-architecture.md:74-80`, `docs/stock-platform-system-architecture.md:219-223`.
- 마지막 상태 유지와 SUSPENDED 표시가 함께 있으나 저장 상태와 표시 상태의 관계가 없다. 중단된 엔진 자신이 정지 상태를 생성할 수는 없다.
- 조치: 독립 감시기 또는 조회 시 effective-status 판정을 설계하고 heartbeat·lastEvaluatedAt·복구 조건을 정의한다.

### F08 · P1 · 현재 신호의 건수·FK 불변식이 다르다

- 근거: `docs/stock-platform-data-model.md:212-246`, `docs/planning/09-database-design.md:44-57`.
- 기존 모델은 symbol UNIQUE, 새 모델은 ticker UNIQUE가 없다. 이벤트가 signal_id와 ticker를 모두 가질 때 동일 종목임을 보장하는 제약도 없다.
- 조치: 종목당 단일 전략인지 다중 전략인지 결정한 뒤 UNIQUE·복합 FK·API·sequence 범위를 함께 확정한다.

### F09 · P1 · 유료 신호는 필드만 숨겨서는 보호되지 않는다

- 근거: `docs/stock-platform-api-contract.md:131-139`, `docs/planning/02-prd.md:53-58`, `docs/planning/08-api-data-contract.md:34`.
- 비구독자에게 BUY 필터를 적용한 종목 목록을 반환하면 방향 필드를 제거해도 목록 자체가 방향을 알려준다. 차트 마커·스크리너·집계·정렬도 같은 문제다.
- 조치: 역할 × 필드 × 필터 × 정렬 × 집계 × 토픽별 권한표를 작성한다. 공개 미리보기가 가상 샘플인지 실제 지연 데이터인지 승인하고 캐시도 권한별 분리한다.

### F10 · P1 · 열린 연결의 권한 회수 계약이 부족하다

- 근거: `docs/stock-platform-system-architecture.md:84-87`, `docs/planning/08-api-data-contract.md:85-87`.
- 만료 즉시 해제 요구는 있지만 연결·재연결 검증만으로는 이미 열린 연결을 차단하지 못한다.
- 조치: 만료·환불·정지·로그아웃의 효력 시점, 캐시 무효화, 복수 게이트웨이 전파, 전송 대기 메시지 처리, 최대 차단 지연·실패 시 기본 거부를 정의한다.

### F11 · P1 · 결제 중복 방지와 역순 처리가 혼재한다

- 근거: `docs/planning/09-database-design.md:93-97`, `docs/planning/08-api-data-contract.md:102`, `docs/stock-platform-data-model.md:343-345`.
- 서로 다른 ID인 환불과 승인 이벤트가 역순 도착하면 이벤트 ID 중복 검사만으로 권한 재활성화를 막을 수 없다.
- 조치: 공급자별 전이표·revision 또는 권위 있는 상태 재조회, 불변 수신 기록과 거래/권한 현재값 분리, 동시 처리·ACK·재시도·대사 규칙을 정한다.

### F12 · P2 · DB 모델을 그대로 migration으로 만들 수 없다

- 근거: `docs/planning/09-database-design.md:13-15,83-91`, `docs/stock-platform-data-model.md:21-24,122-134`.
- UUID PK 대 BIGINT+public UUID, active/disabled 대 ACTIVE/SUSPENDED/DELETED, 목록별 중복 금지 대 사용자별 중복 금지가 다르다.
- 조치: ID 정책·탈퇴 상태·다중 관심목록 여부를 결정하고 ERD, 타입, NULL/default, CHECK/FK, 유일성, 삭제 정책을 채운다. 수급 등 별도 저장소 책임도 명시한다.

### F13 · P2 · PostgreSQL migration 지침을 제약 종류별로 나눠야 한다

- 근거: `docs/stock-platform-data-model.md:397-399`.
- 새 제약조건에 NOT VALID를 일괄 적용할 수 없다. UNIQUE/PK와 FK/CHECK는 절차가 다르며 CREATE INDEX CONCURRENTLY는 트랜잭션 블록에서 실행할 수 없다.
- 조치: 적용 DB 버전과 migration runner에 맞춰 비트랜잭션 단계·실패 인덱스 정리·검증 절차를 별도 명세한다.

## 5. 제품·UX·디자인의 보완점

### F14 · P1 · 구매 이후 사용자 흐름이 빠져 있다

- 근거: `docs/planning/04-user-flow.md:57-71`, `docs/planning/05-wireframe-spec.md:68`.
- 신규 결제 흐름은 있지만 해지·환불·만료·결제수단 실패 후 복구는 상태 이름에 머문다. 처리중 노드에도 명확한 탈출 경로가 없다.
- 조치: 인증 → 구매 → 서버 권한 확인 → 원래 신호 복귀까지 정의한다. 중복 제출 차단·새로고침·다중 탭·장기 지연·문의와 구독 관리 흐름을 추가한다. 미정 환불 정책은 임의 확정하지 않는다.

### F15 · P1 · P0 요구와 프로토타입 범위가 일치하지 않는다

- 근거: `docs/planning/02-prd.md:36-38`, `docs/planning/05-wireframe-spec.md:90-94`.
- 스크리너·관심목록 재방문/삭제·구독 관리는 P0 요구를 검증할 전체 경로가 부족하다.
- 조치: PRD ID → 화면 → 상태 → API → 데이터 → 티켓 → 테스트 추적표를 만든다. 로그인 거절·동의 거절·저장 실패·세션 만료 후 원래 작업 복귀도 포함한다.

### F16 · P1 · MVP와 후속 기능의 경계가 흔들린다

- 근거: `docs/stock-platform-renewal-wireframe-spec.md:116-131`, `docs/planning/02-prd.md:41-44`, `docs/planning/11-mvp-roadmap.md:49-54`.
- 자연어 스크리너·저장·AI 점수·성과의 기본 제공 범위와 고도화 범위가 선명하지 않다. 인사이트/성과의 출시 포함 여부도 PRD와 일정에 명시적으로 연결해야 한다.
- 조치: 기능별 확정/제안/후속/제외를 표시하고, 자연어 처리나 성과 계산을 화면 문구만 보고 추가하지 않는다.

### F17 · P2 · 디자인 계획은 있으나 디자인 설계 결과물은 아직 없다

- 근거: `docs/planning/06-design-plan.md:17-34,90-92`, `docs/planning/05-wireframe-spec.md:79-86`.
- 폰트·컬러·테마 기본값·정확한 스케일이 미정이다. 컴포넌트 목록은 props/동작/반응형/상태 상세 계약이 아니다.
- 조치: 승인용 화면, 컬러·타입·간격·그리드 토큰, 컴포넌트 상태표, 실제 문구, 모바일 예시를 만든다. 문서가 존재한다는 이유로 디자인 게이트를 통과시키지 않는다.

### F18 · P2 · 접근성 원칙을 검증 기준으로 바꿔야 한다

- 근거: `docs/planning/06-design-plan.md:53-62`, `docs/stock-platform-renewal-wireframe-spec.md:176-179`.
- 차트 대체물이 요약 '또는' 표인지 요약 '과' 표인지 다르다. 터치 크기·포커스·실시간 안내의 합격 조건도 구체화가 필요하다.
- 조치: 대비, 최소 타깃 24×24 CSS px 또는 허용 예외, 확대/리플로, 포커스 가림, 키보드 탭·모달·검색, 업데이트 안내·제어를 테스트로 연결한다. 현재 단계에서 WCAG 준수를 선언할 수 없다.

### F19 · P2 · 조사·성공 지표는 가설 수준이다

- 근거: `docs/planning/01-current-state.md:56-67`, `docs/planning/00-brief.md:62-70`, `docs/planning/02-prd.md:72-80`.
- 실제 사용자 조사 부재를 솔직히 적은 점은 좋다. 그러나 관찰 근거 링크와 지표 분모·수집 이벤트·측정 기간·합격 판정이 부족하다.
- 조치: 조사 기록과 가설을 구분하고 역할별 과제·완료 조건·허용 도움·중대한 오해를 정한다. 고객 지불 의사와 시세 라이선스/인프라 비용을 함께 검토해야 월 구독 사업성을 판단할 수 있다.

## 6. 보안·개인정보·운영·실행 계획

### F20 · P1 · 소유권·세션 규칙이 테스트 가능한 수준이 아니다

- 근거: `docs/planning/09-database-design.md:83-85`, `docs/planning/10-security-privacy-compliance.md:20-25`, `docs/stock-platform-api-contract.md:334`.
- 서버 소유권 검증 원칙은 존재하지만 FK만으로 요청자 권한을 보장할 수 없다.
- 조치: 타인 관심목록·결제·해지 거부, 회원 상태별 접근, 세션 폐기, 쿠키 인증 시 CSRF와 스트림 Origin 검증을 명세·음성 테스트에 연결한다.

### F21 · P1 · 개인정보 보존·삭제의 실행 정책이 미정이다

- 근거: `docs/planning/09-database-design.md:129-132`, `docs/planning/10-security-privacy-compliance.md:36-42`, `docs/stock-platform-data-model.md:85`.
- 원본 payload와 최소 payload 요구가 병존한다. 데이터별 보존 기간·삭제 기한·백업 복원 후 삭제 재적용·접근 역할이 없다.
- 조치: 수집 목적/허용 필드/보존 근거/기간/삭제 방식/책임자 표를 승인한다. 법정 기간은 사업 형태·관할 확인 없이 임의 지정하지 않는다.

### F22 · P1 · 법무·라이선스 필수 요건과 예외 승인의 경계가 없다

- 근거: `docs/planning/10-security-privacy-compliance.md:44-52`, `docs/planning/13-tickets.md:84-85,117`.
- 일반 고위험 이슈의 예외 승인과 법률·계약 요건 충족을 혼동할 여지가 있다.
- 조치: 내부 위험 수용으로 대체할 수 없는 출시 조건을 구분한다. 승인자·증빙·문구 버전·데이터 이용 범위·재검토 조건을 기록한다. 미승인 실데이터·신호·성과는 공개하지 않는다.

### F23 · P1 · 티켓은 수직 슬라이스를 선언하지만 실제로는 계층별이다

- 근거: `docs/planning/13-tickets.md:5,21-61,99-110`, `docs/planning/11-mvp-roadmap.md:5`.
- DATA/SIG/AUTH/WEB를 순차 구축하는 구조다. 블로커는 자연어이고 티켓 ID 간 의존성·PRD ID·데모 시나리오가 없다. QA/운영도 마지막 작업처럼 읽힌다.
- 조치: 첫 티켓을 '샌드박스 대표 종목: 로그인→서버 권한→시세/신호→장애 상태'로 잘라 데이터/API/UI/테스트를 함께 묶는다. 관측성과 테스트는 첫 슬라이스부터 포함한다. 병렬 작업은 명시적 의존성 DAG로 관리한다.

### F24 · P2 · 수치화된 기술·운영·일정 기준이 부족하다

- 근거: `docs/planning/07-trd.md:54-57,92-97`, `docs/planning/13-tickets.md:93-97`, `docs/stock-platform-data-model.md:405-410`.
- 기존에는 복구 테스트 요구가 있으나 최종 합격 RPO/RTO, 경보 임계치·호출 대상·동시 사용자·지연 예산이 미정이다. 일정도 인력·처리량·범위 추정 없이 단계만 있다.
- 조치: 공급자 검증 전 임시 목표를 '가정'으로 두고 검증 후 승인한다. 복구/키 교체/웹훅 대사 훈련 결과를 출시 증빙으로 요구한다. 스택 선정 뒤 coding convention을 실행 가능한 lint/typecheck/test/CI 명령으로 구체화한다.

## 7. 권장 수정 순서와 완료 기준

| 순서 | 작업 | 제안 책임 역할 | 완료 증거 |
|---|---|---|---|
| 1 | 문서 정본·MVP 범위·공개 권한 확정 | PO + 기술 리드 | 정본 목록, 역할/필드/필터 권한표 |
| 2 | 신호 방향/상태/평가 revision 계약 | 알고리즘 + 백엔드 + 디자인 | 상태 전이·UI 매핑·이력 불변식 |
| 3 | 순번/replay/원자 저장/권한 회수 | 기술 리드 | 장애 시나리오와 계약 테스트 명세 |
| 4 | 결제 전이·회원/구독 생명주기 | PO + 결제/보안 담당 | 공급자 규약 매핑·사용자 흐름 |
| 5 | API/DB 통합 | 백엔드 + 데이터 담당 | OpenAPI, 이벤트 schema, ERD·데이터 사전 |
| 6 | 고해상도 화면·접근성·사용성 검증 | 디자인 + QA | 프로토타입·토큰·과제별 결과 |
| 7 | PRD 추적표·수직 티켓·운영 예산 | PO + 개발 + 운영 | 요구사항 연결표·DAG·릴리즈 증빙 목록 |

공급자 계약·법무 검토·구독 가격/환불·지원 대상 종목 결정은 위 작업과 병행한다. 가상 데이터 프로토타입과 비공개 기술 검증은 진행 가능하지만 제품 코드 구현은 기존 디자인 승인 원칙을 따른다.

## 9. 최종 판정

- **제품 방향:** 유지할 가치가 있는 일관된 핵심이 있다.
- **기획문서 형식:** 필수 문서와 정본 우선순위를 갖췄다.
- **문서 설계 준비:** 주요 API·상태·권한·replay·결제 충돌은 보강했지만, 승인된 OpenAPI/JSON Schema와 ERD/migration으로 확정하는 단계가 남았다.
- **디자인 승인 준비:** 화면·토큰·프로토타입·사용성/접근성 검증 결과가 추가로 필요하다.
- **개발 인계 준비:** 수직 티켓과 추적표는 보강했지만, 미결정 정책과 provider sandbox 없이는 착수 범위를 고정할 수 없다.
- **상용 출시 준비:** 공급자·결제·법무·개인정보·운영 결정과 검증 없이는 승인할 수 없다.

가장 먼저 해야 할 일은 문서 수를 더 늘리는 것이 아니라 **제안 항목을 승인된 제품 범위·권한표·상태 모델·API/데이터 계약으로 전환하고, 그 결과를 디자인 게이트와 대표 수직 슬라이스로 검증하는 것**이다.
